# DjangoBlog 小组 Python 编码规范

> 课程：软件工程
> 阶段：第 7—8 周
> 班级：软件工程 5 班
> 编写：孙金龙
> 适用范围：DjangoBlog 后续维护与第 9—10 周功能优化

## 1. 总体原则

1. **可读性优先**：代码首先供人阅读，其次供解释器执行。
2. **单一职责**：一个函数只完成一个明确任务，一个 App 只承担一组相关领域职责。
3. **显式优于隐式**：参数、返回值、异常和权限条件应清晰可查。
4. **不重复实现**：跨页面逻辑优先抽取 Mixin、服务函数或模板标签。
5. **安全默认**：登录、CSRF、权限、富文本净化和外部输入校验必须在服务端完成。
6. **改动可验证**：每次功能修改应同步增加或更新测试，并在提交前执行。

## 2. 文件与模块规范

- Python 文件使用 UTF-8 无 BOM 编码。
- 每个模块文件顶部使用简短注释说明模块职责；成员个人标注以姓名缩写开头，例如 `#SJL: 个人精读说明`。
- 模块导入按标准库、第三方库、项目内部模块分组，组间空一行。
- 禁止使用通配符导入，除项目已有后台注册文件外，新增代码必须显式导入。
- 不在模块顶层执行数据库查询、网络请求或耗时文件扫描。
- 迁移文件由 Django 生成，不手工修改历史迁移。

## 3. 命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 模块、包、函数、变量 | 小写蛇形 | `article_list`, `get_current_site` |
| 类、异常 | PascalCase | `ArticleExportView`, `InvalidCommentError` |
| 常量 | 全大写蛇形 | `CACHE_TIMEOUT`, `MAX_PAGE_SIZE` |
| 私有成员 | 单下划线前缀 | `_slug_object`, `_convert_markdown` |
| 布尔值 | 使用 `is_`、`has_`、`can_`、`should_` 前缀 | `is_enable`, `has_reacted` |
| 查询集 | 使用复数或 `_queryset` 后缀 | `published_articles`, `article_queryset` |

不得使用 `dict`、`list`、`str`、`id` 等内置名称作为新变量名；历史代码中的此类命名在维护时逐步替换。

## 4. 注释与文档字符串

### 4.1 模块级注释

模块开头说明模块职责、主要数据和外部依赖。个人负责模块需要带缩写前缀：

```python
#SJL: 项目通用工具模块，包含缓存、Markdown、站点信息和 HTML 净化。
import logging
```

### 4.2 函数级注释

公开函数和复杂私有函数使用 docstring，说明参数、返回值、异常和副作用：

```python
def get_article_markdown(article):
    """将文章转换可下载的 Markdown 文本。

    参数:
        article: Article 模型实例。
    返回:
        str: 包含标题、元数据和原始正文的 Markdown。
    """
```

### 4.3 行级注释

只在解释“为什么”时使用行内注释，不重复代码表面含义。权限判断、缓存失效、并发更新和安全过滤器必须写清楚原因。

## 5. 函数与类设计

- 函数建议不超过 50 行，超过时应提取私有方法或服务函数。
- 一个函数最多接受 5 个位置参数；参数更多时使用数据对象或关键字参数。
- 类视图优先使用 `ListView`、`DetailView`、`FormView` 等 Django 通用视图。
- 可复用请求约束通过 Mixin 组合，但 Mixin 不得隐藏关键数据访问。
- 领域写操作应集中到模型方法、服务函数或表单处理，而不是散落在多个模板标签中。
- 禁止在模板标签中执行不可控的网络请求。

## 6. Django ORM 与数据库

1. 查询外键对象时使用 `select_related`，查询多对多或反向外键时使用 `prefetch_related`。
2. 禁止在循环中逐条查询同一模型。
3. 更新计数类字段使用 `F()` 原子表达式，避免并发丢失更新。
4. 高频筛选字段应配合组合索引，索引顺序遵循“等值条件在前、排序字段在后”。
5. 对可空外键和级联删除必须写明业务原因。
6. 测试数据库与生产数据库配置通过环境变量切换，不把测试数据写入生产库。

## 7. 视图、表单与权限

- 所有写操作必须使用 POST，并由 Django 的 CSRF 中间件或装饰器保护。
- 登录限制优先使用 `LoginRequiredMixin` 或统一视图基类。
- 对象级权限必须在查询阶段或 `get_object()` 阶段完成，不能只依赖模板隐藏按钮。
- 表单字段验证放入 Form/ModelForm；避免只在 JavaScript 中校验。
- 外部参数必须做类型、范围和存在性校验。
- 错误消息应描述用户可采取的下一步，不暴露密钥、SQL 或完整堆栈。

## 8. 异常与日志

- 禁止裸 `except:`；必须捕获具体异常。
- 允许降级的外部服务调用可捕获 `Exception`，但必须使用 `logger.exception` 或 `exc_info=True` 记录堆栈。
- 业务异常与程序异常分开处理；可预期错误返回 400/403/404，未知错误返回 500。
- 日志不得记录密码、Token、AppSecret、完整 Cookie。
- 邮件、搜索和 CDN 等非核心外部服务的失败不应破坏已成功的本地数据库事务。

## 9. 安全要求

- `SECRET_KEY`、数据库密码、OAuth AppSecret 和邮箱密码必须由环境变量或本地未提交配置提供。
- 富文本进入页面前必须经过 Bleach 白名单净化。
- 上传文件必须校验扩展名、大小和存储路径，最终路径必须位于目标目录内。
- 模板默认自动转义；只有经过净化或可信 HTML 才能使用 `safe`。
- 外部链接使用 `rel="nofollow"` 或相应安全属性。
- 不把对象权限仅放在前端按钮状态中。

## 10. 缓存规范

- 缓存键使用 `CacheKey` 或稳定前缀，避免相同业务出现多个拼写。
- 写操作成功后清理受影响的列表、详情、侧栏和 SEO 缓存。
- 不得缓存未授权的私有数据。
- 缓存值必须有合理过期时间；允许空值缓存时应使用专用哨兵值。
- 清理缓存失败应记录日志，但不能悄悄返回错误数据。

## 11. 模板与前端

- 模板只负责展示和简单条件判断，不写复杂业务计算。
- 可复用页面片段放回对应 App 的 `tags/` 目录。
- CSS class 统一使用项目现有 Tailwind/Bootstrap 约定。
- JavaScript 请求必须处理成功、失败和网络异常状态。
- 表单按钮在提交后应提供处理中或禁用状态，避免重复提交。

## 12. 测试规范

- 每个新增视图至少覆盖未登录、无权限、成功和非法参数场景。
- 每个新增模型方法至少覆盖正常值、边界值和异常值。
- 外部 API 使用 Mock，不在单元测试中访问真实 SMTP、OAuth 或 Elasticsearch。
- 测试方法名称应描述业务条件和预期结果。
- 测试数据在 `setUp()` 或工厂函数中创建，测试之间不得共享可变数据。

## 13. Git 与提交规范

- 分支使用 `成员姓名首字母_branch`，孙金龙使用 `sjl_branch`。
- 提交前执行 `git status`、语法检查和相关测试。
- 每个提交只包含一个阶段或一类修改。
- 提交信息格式：`type(scope): 说明`。
- 常用类型：`feat`、`fix`、`docs`、`test`、`refactor`、`chore`。
- 不提交虚拟环境、日志、数据库备份、缓存、密钥或个人 IDE 配置。

示例：

```text
docs: 完成第6周系统架构与泛读报告
fix(blog): 使用原子更新修正浏览量并发丢失
test(blog): 覆盖文章 Markdown 导出权限
```

## 14. IDEA 2023 / PyCharm 检查配置

1. 打开 `Settings → Editor → Inspections`。
2. 启用 Python 的 PEP 8、未使用导入、未解析引用、重复代码和类型检查。
3. 启用 Django 模板和 SQL 检查。
4. 使用 `Code → Inspect Code` 扫描 `src/DjangoBlog-master`。
5. 使用 `Code → Reformat Code` 前先确认团队缩进统一为 4 个空格。
6. 对严重和警告级别问题分批处理，不在同一提交中做无关全局格式化。
