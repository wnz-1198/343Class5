# 小组 Python 编码规范（第 7-8 周小组交付物）

> 组号：5 ｜ 项目：DjangoBlog ｜ 依据：PEP 8 + 本项目质量分析结论 + 小组实际约定
> 适用范围：本组所有成员对 DjangoBlog 项目的精读标注、维护优化与新增功能开发
> 执行方式：新代码必须遵守；修改存量代码时"顺手规范"，不做无意义的大面积重写

## 1. 代码风格

1. **缩进与行宽**：4 空格缩进，禁用 Tab；单行不超过 120 字符（本仓库多数文件现状，比 PEP 8 的 79 宽，保持一致）。
2. **命名**：
   - 模块/包名全小写下划线（`sensitive_words.py`）；类名 PascalCase（`CommentPostView`）；
   - 函数/变量小写下划线（`check_sensitive_words`）；常量全大写（`SENSITIVE_WORDS`）；
   - 模型字段、表单字段与数据库/表单语义一致，不使用拼音缩写。
3. **导入**：按 标准库 → Django → 第三方 → 本项目 分组，组间空一行；**禁止 `from xxx import *`**（存量 admin.py 等处逐步替换为显式导入）。
4. **字符串**：优先 f-string；拼接 SQL 语句一律禁止（必须使用 ORM 参数化查询）。
5. **工具**：提交前用 IDE 的 SonarQube for IDE 插件自查，不引入新增 Code Smell。

## 2. 注释规范（小组考核项）

1. 每个模块文件头部写模块级说明（职责、对外接口）。
2. 每个人的注释以**姓名缩写前缀**打头，形如 `# DB: ...`（本成员对应关系见分工表：#ZZC/#DB/#WNZ/#XLT/#SJL）。
3. 类、函数必须有 docstring：说明用途、参数、返回值；复杂逻辑块用行注释说明"为什么"而不是复述代码。
4. 注释与代码同步更新，禁止留下与代码不符的注释；废弃代码直接删除，不注释保留。

## 3. 异常与日志

1. **禁止裸 `except:`**；捕获范围尽量精确（如 `AttributeError, IndexError, TypeError`）。
2. `except Exception` 仅允许出现在：①系统边界（视图/中间件/信号入口）；②异步/后台任务（防止线程崩溃），且必须 `logger.error` 记录。
3. 所有外部请求（requests 等）**必须设置 timeout**（本项目现有惯例 `timeout=2`，可按场景调整）。
4. 日志统一使用 `logging`（模块级 `logger = logging.getLogger(__name__)`），禁止 `print` 调试输出入库；生产路径禁止残留调试注释。

## 4. Django 专项约定

1. **模型**：迁移文件必须与 models.py 同步提交；新增查询条件若高频使用，配套定义**具名组合索引**（如 `idx_art_parent_enable` 命名法：idx_列缩写_列缩写）。
2. **视图**：优先 CBV；对象不存在用 `get_object_or_404`；用户输入校验放在 Form 层（字段白名单），视图层不重复造轮子。
3. **信号**：模型保存后的缓存失效、通知等副作用统一挂 post_save 信号；**注意 `queryset.update()` 不触发信号**——需要触发副作用的写操作必须逐条 save。
4. **缓存**：缓存空值判断用 `is None`，不要把空列表/空串当未命中；写缓存注意与信号清理路径一致。
5. **安全**：模板输出转义默认开启；HTML 白名单净化用 bleach；所有 JSON 接口显式校验登录与参数白名单；秘密配置不硬编码，走环境变量/`local_settings`。

## 5. 测试要求

1. 每个新功能必须带测试：视图行为测试 + 纯函数单元测试（参考 `comments/test_sensitive_words.py` 的分层写法）。
2. 断言必须精确到期望状态码/数据状态，**禁止 `[200,302,403,500]` 这类弱断言**（质量分析报告 Q9 教训）。
3. 测试基类复用 `djangoblog.test_base.BaseTestCase`，禁止在多个测试类里复制 setUp。
4. 提交前在本地跑通所属 app 的测试（无 MySQL 环境可用 SQLite 内存库配置）。

## 6. Git 协作规范

1. **分支**：每人一个 `姓名缩写_branch` 个人分支；工作在个人分支进行，经 PR 由组长审核后合入 master/main。
2. **提交信息**：`类型(模块): 个人标识 - 周次 摘要`，类型取 docs/feat/style/fix；示例：
   `feat(comments): DB个人作业 - 第9-10周 评论敏感词过滤功能`
3. **提交粒度**：文档、功能、注释风格调整分开提交；禁止把个人环境配置（`.idea/`、本地 settings 数据库段）提交入库。
4. **合并纪律**：PR 描述写清改动范围与测试情况；合并前确认不与 master 产生冲突，远端有更新先 rebase。

## 7. 下一步系统优化计划（结合质量分析报告）

按质量分析报告问题清单优先级推进：
1. Q1：admin 批量审核改为逐条 save，恢复信号触发的缓存清理与通知；
2. Q2：回复评论增加父评论归属/启用/存在性校验；
3. Q4/Q5：敏感词过滤（第 9-10 周已实现）→ 评论频率限制；
4. Q6-Q10：查询合并、冗余查询消除、`__str__` 截断、测试断言收紧、i18n 统一。
